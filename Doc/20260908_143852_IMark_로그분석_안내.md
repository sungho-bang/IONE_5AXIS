# I-Mark 로그 분석 안내

작성: 2026-09-08 / 대상: Git_IONE_5AXIS, X1135, Schema=IMarkV2

## 1. 분석할 파일

실제 운전 로그의 기본 경로:

```text
D:\Works_Updates\대주이엔지\Git_IONE_5AXIS\FAFramework\bin\Debug\Log\VT3500\IMarkLog\YYYY\MM\YYYY-MM-DD.log
```

같은 날짜의 다음 파일도 함께 있으면 정지 원인과 설비 전체 동작을 대조할 수 있다.

- `Log\VT3500\TraceLog\YYYY\MM\YYYY-MM-DD.log`
- `Log\VT3500\AlarmLog\YYYY\MM\YYYY-MM-DD.log`
- `Log\VT3500\StateLog\YYYY\MM\YYYY-MM-DD.log`
- 기록 실패 확인: `Log\SystemLog\YYYY\MM\YYYY-MM-DD.log`

현재 IMarkLog 보관 설정은 7일이다. 실행 위치가 달라지면 로그 기본 경로도 달라진다.

## 2. 읽는 순서

1. 문제가 발생한 시간 전후에서 `Event=START`를 찾는다.
2. 해당 행의 `RunId`를 복사해 같은 RunId의 기록을 모은다. 시퀀스 실행마다 ID가 다르다.
3. `Seq`, `Caller`, `Job`, `UseIMark`로 실제 실행 경로와 사용 설정을 확인한다.
4. START 행에서 `AutoTimeoutMs`, `InitialTimeoutMs`, `RetryLimit`, 위치/속도/가감속 설정을 확인한다.
5. `MODE_SELECTED` 또는 `BYPASS`를 확인한 후 단계, 입력, 감지, 재시도, 알람, 종료 순서를 읽는다.
6. `TIMEOUT_RETRY`의 TimeoutNumber, 센서 값, ActualPos/CommandPos를 비교한다.
7. `RETRY_EXHAUSTED_ALARM`에 도달하면 AlarmId를 같은 시각의 AlarmLog와 비교한다.
8. 정상 종료가 없으면 `ABORTED`, `SUSPENDED`, `STATE_RESET_OR_ENDED`, HEARTBEAT의 마지막 단계와 모터 상태를 확인한다.

## 3. 필드 뜻

| 필드 | 의미 |
|---|---|
| Schema | 새 상세 로그 형식 `IMarkV2` |
| RunId | 한 시퀀스 실행을 연결하는 고유 ID |
| Seq / Caller | 현재 시퀀스 / 호출한 상위 시퀀스 이름 |
| Event | START, 입력 변화, 감지, 타임아웃 등 사건 종류 |
| ElapsedMs | 해당 시퀀스 시작 이후 경과시간. 일시정지 시간도 포함 |
| Step / StepName / Action | 현재 단계 번호, 기존 단계명, 추가 설명명 |
| Sensor | On / Off / Unknown / NULL / READ_ERROR |
| ExpectedIO / InputName / InputIndex | 기대 IO=X1135와 실제 연결된 IO의 이름/숫자 인덱스 |
| RawInput / CorrectedInput / IOInverse | 원 입력, IO 반전 적용 값, IO 반전 여부 |
| InputInverse | 센서 레벨의 추가 반전 설정. START에서 확인 |
| UseIMark / Job / ProductId | 현재 메모리의 사용 설정 / 선택 JOB 이름 / 제품 ID |
| ActualPos / CommandPos | 최근 읽힌 실제 위치 / 명령 위치 |
| DetectedPos | ON 판단 후 정지 요청 직전에 읽은 실제 위치 |
| RunFlag / MotionDone / ServoOn / ServoAlarm | 모터 상태 피드백 |
| FastMoveState / SlowMoveState | 이동 하위 시퀀스의 상태 |
| FastMoveError / SlowMoveError / LastError | 이동/현재 시퀀스가 보유한 마지막 오류 문자열 |
| TimeoutNumber | 이번 타임아웃 차수. 최종 제한 판정 후 카운터 0 초기화와 별도로 보존 |
| RetryCount / RetryLimit | 런타임 재시도 카운터 / 설정된 제한값 |
| WaitMs | 자동/초기화 감지 단계의 타임아웃 또는 자동 감지까지의 단계 경과시간 |
| CurrentCount / ManualCount / CuttingCount | 자동/수동 로딩 카운트 및 UI 컷팅 카운트 |
| Key / Count | 동일 반복 이벤트의 키와 누적 발생 횟수 |

센서/IO 값은 각 속성을 읽는 시점의 값이다. 하드웨어에서 동일 시각에 래치한 원자적 스냅샷은 아니다. 매우 빠르게 변하는 입력에서는 DecisionInput과 뒤이어 읽은 Sensor/RawInput이 다를 수 있다.

`TERMINATED`는 종료 콜백이 실행되었다는 뜻이다. 프레임워크는 콜백 이후 State를 변경하므로 같은 행의 SeqState가 Running일 수 있다. 취소 경로도 종료 콜백을 거칠 수 있으므로 USER_CANCEL/알람/중단 이벤트와 함께 판단한다.

## 4. 전형적인 사건 순서

자동 정상 감지:

```text
START
MODE_SELECTED  Mode=AutomaticOrOneCycle
STEP_ENTER     Action=FAST_MOVE_WAIT_COMPLETE
STEP_ENTER     Action=SLOW_SEARCH_COMMAND
STEP_ENTER     Action=WAIT_IMARK
DETECTED_STOP_REQUESTED  DecisionInput=On;DetectedPos=...
FEED_COUNTED_STOP_REQUESTED
STEP_ENTER     Action=HOME_RESET_FINAL
TERMINATED
```

입력 변화는 실제로 관측했을 때 INPUT_CHANGED로 추가된다. 시작 전부터 ON이었다면 OFF→ON 변화 행 없이 감지가 성립할 수 있다.

자동 미감지 / 현재 제한값 3:

```text
TIMEOUT_RETRY          TimeoutNumber=1
HOME_RESET_RETURNED
TIMEOUT_RETRY          TimeoutNumber=2
HOME_RESET_RETURNED
RETRY_EXHAUSTED_ALARM  TimeoutNumber=3;AlarmId=2005002
```

I-Mark 미사용:

```text
START                 UseIMark=False
BYPASS                Reason=UseIMarkFalse
STEP_ENTER            Action=BYPASS_FAST_MOVE
STEP_ENTER            Action=BYPASS_SLOW_MOVE
FEED_COUNTED_STOP_REQUESTED
TERMINATED
```

무제한 수동 탐색 중:

```text
MODE_SELECTED  TimeoutApplied=false;RetryLimitApplied=false
SEARCH_REPEAT  Count=1
HEARTBEAT      ElapsedMs=...
SEARCH_REPEAT  Count=...
...
DETECTED_STOP_REQUESTED 또는 ABORTED
REPEAT_TOTAL   Count=...
```

위 예시는 읽는 방법을 보여주는 축약이다. 별도로 저장한 `20260908_143852_IMark_모의실행_원본로그.log`는 실제 수정 코드를 모의 입력으로 실행해 생성한 기록이며, 생산 중 수집한 실물 설비 로그가 아니다.

## 5. 증상별 확인

| 증상 | 우선 확인 |
|---|---|
| I-Mark를 사용한 것 같은데 그냥 이송함 | START의 UseIMark, BYPASS 여부, Seq가 단계 수동인지 확인 |
| 고속 이동 때 마크를 봤는데 정지하지 않음 | INPUT_CHANGED가 고속 단계인지 확인. 기존 제어는 저속 감지 단계에서 ON을 판단 |
| 탐색하자마자 정지 | START/INPUT_INITIAL부터 ON인지 확인. 기존 제어는 ON 엣지가 아닌 레벨 검사 |
| 계속 재시도 | Seq, Mode, RetryLimitApplied 확인. 일부 수동/초기화는 무제한 반복 |
| 센서가 OFF인 것과 누락을 구분하고 싶음 | Sensor=NULL / Unknown / READ_ERROR / InputMapping=MISSING 구분 |
| 세 번째 실패인데 RetryCount=0 | IncreaseCount가 제한 도달 시 초기화함. TimeoutNumber=3과 AlarmId 확인 |
| 정지 요청했는데 이송이 남음 | DETECTED_STOP_REQUESTED 이후 RunFlag/MotionDone/MOTION_CHANGED와 좌표 초기화 순서 확인 |
| 위치값이 갑자기 0 | HOME_RESET 관련 단계/이벤트 확인. 물리 원점 복귀와 위치 카운터 초기화를 구분 |
| 로그 파일이 없음 | 실행 파일 위치, 새 빌드 적용 여부, 해당 시퀀스 실행 여부, SystemLog의 Log write failed 확인 |
| 마지막 행이 HEARTBEAT이고 다음이 없음 | 해당 시점 이후 프로세스/스케줄러 중단 또는 저장 실패 가능성. 다른 로그와 함께 확인 |

## 7. 기록 범위와 한계

- 5개 대상 시퀀스가 활성인 동안 소프트웨어 스케줄러가 관측한 입력/모터 상태를 기록한다. 설비 전체 시간의 IO 파형 기록기는 아니다.
- 스캔 사이에 발생하고 사라진 매우 짧은 펄스는 로그에서 확인할 수 없다.
- 정지 요청과 완전 정지는 다르다. 기존 제어에 별도 정지 완료 대기가 없는 구간에서는 로그만으로 정지 정밀도를 확정할 수 없다.
- 반복 로그는 5초 간격 누계이고 종료 시 총계가 기록된다. 개별 반복 전체의 시간/위치를 모두 저장하지 않는다.
- 비동기 기록이므로 강제 종료 직전의 큐 기록은 남지 않을 수 있다. 원인 추정 시 로그가 없다는 사실만으로 동작이 없었다고 단정하지 않는다.
- 기본 보관 기간은 7일이며 오래된 기록은 자동삭제될 수 있다.
